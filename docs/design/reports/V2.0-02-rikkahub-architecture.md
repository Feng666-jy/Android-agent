# 《RikkaHub 架构可借鉴部分》

> 来源：github.com/rikkahub/rikkahub（Kotlin + Jetpack Compose + Koin + Room，AGPL-3.0）
> 原则：只提取架构思想与模块设计，不复制 UI / 业务代码。
> 关键模块：`:ai`（SDK 抽象）、`:workspace`（proot Linux 沙盒）、`app/data/ai`（Agent 运行时：GenerationHandler / tools / mcp / transformers）。

---

## 1. Agent Core 设计（GenerationHandler）

**核心思想：把"生成"建模为带状态机的 Step Flow，而不是一次 LLM 调用。**

- `generateText(...): Flow<GenerationChunk>` — 整个 Agent 循环是 Flow，UI 订阅增量渲染；`GenerationChunk.Messages` 每步发射整条消息列表（含工具进度）。
- 循环上限 `maxSteps = 256`（可配），每轮：
  1. 按 Assistant 配置动态组装工具（记忆工具按需注入、MCP 工具、本地工具、工作区工具）
  2. `generateInternal` 调 Provider 流式生成（支持工具调用）
  3. 检查最后一条消息中的 Tool parts：未执行 → 判定审批状态机
  4. **审批状态机**：`Auto → Pending`（需人工）→ `Approved / Denied / Answered(ask_user)`；Pending 则 break 等待用户，恢复时跳过生成直接续跑
  5. 执行已批准工具，**结果合并回原 assistant 消息的 Tool part**（不产生独立 tool 消息），截断工具输出（32KB 全量 / 4KB 预览）
  6. 循环直到无工具或完成
- 上下文管理：`limitContext()` 阶梯式截断；`UIMessage` 统一消息模型，`MessageNode` 支持分支（每条消息可有多版本 + selectIndex）。

**可借鉴**：
- Agent 循环 = Flow/流式事件源，天然支持 UI 实时进度与 HITL 暂停/恢复。
- 工具执行结果回填到消息树而非扁平追加，为"分支/重试/回看"打基础。
- 审批是"消息状态机"而非独立队列 —— 恢复时从最后一条消息续跑。

## 2. Tool 系统（ai/core/Tool.kt）

**核心思想：Tool 是声明式 DSL，且"是否审批"由调用参数动态决定。**

```kotlin
data class Tool(
    val name: String,
    val description: String,
    val parameters: () -> InputSchema? = { null },          // 惰性 JSON Schema
    val systemPrompt: (model, messages) -> String = { _, _ -> "" }, // 按工具动态注入提示词
    val needsApproval: (JsonElement) -> Boolean = { false }, // 按本次参数决定是否审批！
    val execute: suspend (JsonElement) -> List<UIMessagePart> // 返回结构化 parts
)
```

- 工具按类别组织：`LocalTools`（JS 引擎 / 时间 / 剪贴板 / TTS / ask_user / 屏幕时间 / 日历）、`WorkspaceTools`（read/write/edit/shell）、`MemoryTools`（create/edit/delete）、`SearchTools`、`SkillsTools`、`ConversationTools`。
- `ask_user` 是内置 HITL 工具：LLM 主动提问，用户回答作为 `Answered` 状态回到循环 —— **交互不是审批弹窗的附属品，而是工具**。
- 工具输出是 `List<UIMessagePart>`（Text/Image/Diff/Tool...），可携带图片、diff 等富结果。

**可借鉴**：
- 工具注册表 + 分类工厂（`getTools(options)` 按配置组装）。
- `needsApproval(args)` 参数级动态审批（比当前静态 allow/ask/deny 更细）。
- per-tool `systemPrompt` 注入（工具自带使用说明）。
- 工具结果结构化（parts），为 Vision 图像结果、文件 diff 展示铺路。

## 3. Android 能力封装方式（:workspace 模块）

**核心思想：一个"沙盒工作区"门面（WorkspaceManager）暴露文件系统 + Shell 两种能力，工具只是薄封装。**

- `WorkspaceManager`：统一入口（listFiles/readText/writeText/importFile/exec），内部 `WorkspaceFileSystem`（路径校验、大小上限、`maxListEntries/maxSearchResults`）与 `WorkspaceShellRunner`（接口）。
- Shell 双实现：`ProotShellRunner`（真 Linux rootfs：RootfsInstaller 下载解压 + RootfsPatcher 修补 + proot 原生二进制）+ `HostShellRunner`（回退）。
- 每个 Workspace 独立目录（files / linux / temp 三个区），支持 bind mounts，`WorkspaceShellStatus`（DISABLED/INSTALLING/READY/BROKEN）状态机。
- 工作区工具审批：`WorkspaceToolDefaultApprovals`（read/write/edit 默认不审批，shell 默认审批）+ 每个 workspace 可持久化 `toolApprovalOverrides`。

**可借鉴**：
- "能力 = 门面 Manager + 策略可替换的 Runner 实现"，工具层只做参数解析与结果包装。
- 权限默认值按工具危险性分级（读 < 写 < 执行）。
- 重型环境（rootfs）有安装/状态机，对 Android Runtime 的设备能力初始化（Accessibility 就绪/Shizuku 就绪）同理。

## 4. 权限控制方式

**三层设计**：
1. **声明层**：`Tool.needsApproval: (args) -> Boolean` — 每次调用动态判定。
2. **状态层**：`ToolApprovalState`（Auto/Pending/Approved/Denied/Answered）挂在 UIMessagePart.Tool 上，随消息持久化。
3. **策略层**：默认审批表 + 每 workspace 覆盖（`resolveWorkspaceToolApproval(name, overrides)`）。

**可借鉴**：权限 = 静态默认 + 动态谓词 + 实例级覆盖；审批状态随消息存储（可审计、可恢复），比内存队列更可靠。

## 5. Provider 抽象（:ai 模块）

**核心思想：无状态 Provider 接口 + 注册表 + 模型能力 DSL。**

- `interface Provider<T : ProviderSetting>`：`listModels / generateText / streamText / generateEmbedding / generateImage / editImage`；无状态，setting 每次传入。
- `ProviderManager`：`registerProvider(name, provider)` / `getProviderByType(setting)` 注册表模式。
- `ModelRegistry`：DSL 按模型名 token 推断能力（vision / tool / reasoning），如 `defineModel { tokens("gpt","5"); visionInput(); toolReasoningAbility() }` —— 不靠手工维护能力矩阵。
- 传输层：OkHttp + SSE 解析器；`KeyRoulette` 密钥轮换（多 Key 池）；`ErrorParser` 统一错误解析。

**可借鉴**：Provider 注册表（当前 factory 已接近）；能力 DSL（当前 models.capabilities 是手工 JSON，可升级为按模型名自动推断）；密钥池/轮换（商业化必备）。

## 6. Memory 设计

**核心思想：记忆 = 结构化条目 + 工具操作 + 系统提示注入，按"助手"或"全局"隔离。**

- `AssistantMemory(id, content)` + `MemoryRepository`（Room DAO）+ `GLOBAL_MEMORY_ID = "__global__"`。
- `memory_tool`：`create / edit(id) / delete(id)` 三个动作；描述里写清**什么该存、什么不该存**（隐私红线）、**相似记忆合并**、今日日期注入。
- 启用记忆时，历史记忆以 `<memories>` 标签自动注入 system prompt；`enableMemory` / `useGlobalMemory` 是 Assistant 配置项。
- 记忆由 LLM 主动维护（对话中自动增删改），非后台异步抽取 —— 简单可靠。

**可借鉴**：记忆工具化 + 注入化 + 作用域（agent/global）化；先做"条目记忆"，检索增强（向量）后续再加。

## 7. Workflow 设计（对应能力）

RikkaHub 没有独立 Workflow 引擎，其"可组合性"由 **Assistant 配置单元**承担：
- Assistant = systemPrompt + 模型参数 + 工具集（MCP servers / local tools / skills / workspace）+ 记忆开关 + 正则转换 + 模式注入（mode/lorebook）+ 上下文条数上限 + 消息模板。
- 会话侧还有 MessageNode 树（分支）、transformer 流水线（输入侧 Template/OCR/Document，输出侧 Think/Regex）。
- 消息转换管线（MessageTransformer）是"处理链"思想：请求前/响应后各一串转换器，可插拔、可组合 —— 这是轻量版"工作流"。

**可借鉴**：Agent = 可配置单元（agent 表）；transformer 管线可演进为 Workflow 节点；MessageNode 树可演进为会话分支。

---

## 8. MCP / Skill（顺带）

- **MCP**：`McpManager`（配置协调 + OAuth + 状态）→ `McpSessionRegistry`（每 server 一个连接状态机：connect / 指数退避重连 / Stale 配置识别 / NeedsAuthorization）→ 传输层（SseClientTransport / StreamableHttpClientTransport）；MCP 工具以 `serverId:toolName` 前缀合入工具表。
- **Skill**：`enabledSkills` 配置 + `SkillsTools`（`read_skill` 工具读 SKILL.md 与包内文件，含路径越界防护）。

**可借鉴**：MCP 会话注册表 + 状态机（重连/鉴权态）值得原样建模；Skill = 目录包 + 工具暴露 + 可见性开关。

## 结论（RikkaHub 对 V2.0 的贡献点）

| 贡献点 | 落地位置 |
|--------|----------|
| Flow/事件流式 Agent 循环 + 步骤状态机 | Agent Core V2（Loop + Events） |
| 参数级动态审批 needsApproval(args) + 审批状态随消息 | Permission Layer V2 |
| Tool DSL（惰性 schema / per-tool prompt / 结构化输出） | Tool Router |
| Provider 注册表 + 模型能力 DSL + Key 池 | LLM Provider 层 |
| 记忆工具化 + `<memories>` 注入 + 作用域 | Memory System |
| MCP 会话注册表 + 重连状态机 | MCP 层 |
| Skill 包 + 可见性 + 越界防护 | Skill 层 |
| 门面 Manager + 可替换 Runner 封装设备能力 | Android Runtime |
