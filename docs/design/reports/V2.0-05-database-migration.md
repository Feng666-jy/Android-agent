# 《数据库升级设计 V2.0 + 迁移方案》

> 原则：**只做增量（CREATE TABLE / ADD COLUMN），绝不破坏已有数据**；迁移可重复执行（幂等）。
> 现状：运行时是 node:sqlite + `SCHEMA_SQL`（CREATE TABLE IF NOT EXISTS，无 ALTER）；`prisma/migrations/0001_init` 存在但运行时未使用。
> 结论：新增"迁移运行器"（scripts/migrate.ts + _migrations 表），后续所有变更走 migration 文件，`SCHEMA_SQL` 只保留基线。
> ✅ **实施状态（2026-08-12）**：Phase 0 已落地 —— 迁移运行器 + `0002_agent_v2` 已应用到 dev.db（自动备份、数据完整、幂等验证通过、7 个迁移测试）。本节 1/2 为最终目标设计；3 为已实施与后续迁移规划。

## 3. 迁移方案（不破坏数据）

### 3.1 迁移运行器（✅ 已实施）

```
scripts/migrate.ts + server/src/db/migrate.ts
  - 读取 prisma/migrations/*/migration.sql（按目录名排序）
  - _migrations 表记录已应用迁移（name, applied_at）
  - 首条迁移 = 基线：库中已存在 users 表 → 只记录不执行（兼容旧 dev.db / SCHEMA_SQL）
  - 单迁移事务执行，失败整体回滚；应用前自动备份 *.db.backup-<时间戳>
  - 已应用迁移不可修改；新增变更一律 0003+ 新迁移
```
- 命令：`npm run db:migrate`；`npm run db:init` 已集成（dev:all 全链路自动应用）。
- `SCHEMA_SQL`（server/src/db/schema.ts）**不再承载新表**，只保留基线；新结构全部由迁移管理。
- `fieldmaps.ts` 同步登记新表字段（Prisma 兼容层需要）。

### 3.2 已实施迁移 0002_agent_v2（✅）

范围（Phase 0）：
1. Agent 运行时表对齐（IF NOT EXISTS）：`agent_runs` / `agent_messages` / `agent_tool_calls` / `agent_token_usages` —— 修复"只存在于 SCHEMA_SQL、0001 缺失"的漂移。
2. 新表：`conversations` / `messages` / `agent_steps`。
3. `agent_runs` 增列：`conversation_id` / `agent_id` / `plan_json`（可空）。
4. 索引：会话/消息/步骤/运行查询索引（IF NOT EXISTS）。

实施验证（2026-08-12）：
- dev.db 迁移成功：`applied=0002_agent_v2, skipped=0001_init (baseline)`；自动备份 `dev.db.backup-20260812-014822`。
- 数据完整：users=1 / providers=1 / agent_runs=2 / agent_messages=10 与迁移前一致。
- 幂等：二次运行 `applied=0`。
- 测试：`npm test` 218 项（215 pass + 3 skip），新增迁移测试 7 项全过。

### 3.4 兼容性要点

1. **绝不 DROP / 重建**存量表；不重命名列。
2. `prisma/schema.prisma` 与 `server/src/db/fieldmaps.ts` 同步更新（schema.prisma 为权威定义，迁移 SQL 与之核对）。
3. 老接口 `/api/agent/*` 继续读旧表；v2 新增表与旧表通过 `agent_runs.conversation_id` 桥接。
4. 数据回填脚本（可选）：把历史 run 迁移成 conversation 只读视图（不强制）。
5. MySQL 生产库：同构迁移由 prisma migrate 生成；node:sqlite 兼容层仅用于开发/单机。
